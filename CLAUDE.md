# Claude Development Guidelines

## Project Overview

ImapFlow is a modern, promise-based IMAP client library for Node.js. It opens
TLS/cleartext connections to IMAP servers, authenticates, and parses untrusted
protocol responses from those servers into a friendly API. It is written in
TypeScript under `src/` and published to npm as `imapflow` as a dual package:
ES modules in `dist/esm/` and CommonJS in `dist/cjs/`, each with its own type
declarations. Both `import { ImapFlow } from 'imapflow'` and
`const { ImapFlow } = require('imapflow')` work.

## Project Structure

- `src/imap-flow.ts` - Main `ImapFlow` client class (connection lifecycle, command dispatch, public API). The package entry point: exports `ImapFlow`, `AuthenticationFailure`, `ImapFlowErrorCode`, the transport factories `createStreamsTransport` and `createSocketsTransport`, every public type, and a default export object `{ ImapFlow, AuthenticationFailure }`
- `src/types.ts` - Public data shapes (`ImapFlowOptions`, `MailboxObject`, `FetchMessageObject`, `SearchObject`, events, ...). Re-exported from the entry point
- `src/errors.ts` - `ImapFlowError` (an Error with the optional extra properties the library attaches: `code`, `response`, `responseStatus`, `serverResponseCode`, ...) and the `AuthenticationFailure` class
- `src/imap-commands.ts` - Registry wiring individual command implementations
- `src/commands/` - Per-command implementations (login, fetch, search, append, etc.), one default-export async function each
- `src/handler/` - IMAP response stream parser and command compiler (tokenizer, literals, line handling); `src/handler/types.ts` holds the protocol shapes (`ImapResponse`, `ImapAttribute`, ...)
- `src/download.ts` - The `download()` and `downloadMany()` implementations, built on the public `fetchOne()`
- `src/search-compiler.ts` - Translates the search query object into IMAP SEARCH terms
- `src/charsets.ts`, `src/jp-decoder.ts` - Charset/encoding helpers
- `src/special-use.ts` - SPECIAL-USE mailbox detection
- `src/proxy-connection.ts` - SOCKS/HTTP proxy connection support
- `src/streams-transport.ts` - `createStreamsTransport(api)`, the `transport` option over any socket API built on web streams (`open()` and an optional `upgrade()`): wraps the streams into a net.Socket-like Duplex, and holds reads once a STARTTLS OK arrived because a runtime may not start TLS with a read in flight. New socket APIs get an adapter on top of it, not a change of the `ImapTransport` interface
- `src/sockets-transport.ts` - `createSocketsTransport(connect)`, the adapter of the `cloudflare:sockets` API (celld, Workers) to `createStreamsTransport()`, refusing the TLS options the runtime can not honor
- `src/limited-passthrough.ts`, `src/tools.ts`, `src/logger.ts`, `src/connection-deadline.ts` - Internal utilities. `tools.ts` also holds the helpers every command shares: `isAuthenticatedState()` and `getSelectedMailbox()` for the state precondition (the latter also narrows the mailbox type, so do not cast `connection.mailbox`), `reportCommandError()` for the failure path, and `emitSafe()` for state-change events emitted inside the command pipeline
- `src/package-info.ts` - Generated by `scripts/build.js` from `package.json` (`name`, `version`, `homepage`). Gitignored and regenerated by `npm run build` and `npm run typecheck`. Never import `package.json` from `src/`
- `src/vendor-types.d.ts` - Minimal ambient declarations for the runtime dependencies that ship without types (libmime, libqp, libbase64, encoding-japanese)
- `scripts/build.js` - The build: generates `src/package-info.ts`, runs `tsc` with `tsconfig.esm.json` and `tsconfig.cjs.json`, writes a `package.json` with the module format into each output directory, and rewrites CommonJS modules that only have a default export so `require()` returns the function or class itself
- `dist/` - Build output, gitignored; it is what gets published to npm (`src/` is not part of the package)
- `test/` - TypeScript tests (`*-test.ts`), run with `node --import tsx --test`. `test/fixtures/` holds shared helpers (`mock-connection.ts` is the mock connection the command tests run against), `test/commands/` has one file per command in `src/commands/`, `test/package/` checks the built `dist/` output and its type declarations, `test/imapkit/` runs sessions against ImapKit in-process (part of `npm test`), `test/integration/` needs Docker, `test/cloudflare/` runs the build on workerd through wrangler (its own job, see below), `test/celld/` runs it on celld in Docker (`npm run test:celld`), `test/browser/` bundles it for headless Chrome (`npm run test:browser`)
- `examples/` - Standalone usage examples (not production code, not linted). Type-checked with `checkJs` against the built declarations by `test/package/examples-test.ts` (`tsconfig.examples.json`)

## Technology Stack

- **Runtime**: Node.js 20 or newer (`engines.node`), CI tests on 20.x, 22.x and 24.x. The ES module build is also supported on Bun (latest release, full suite in CI) and on Cloudflare Workers with `nodejs_compat` (see "Other runtimes" below)
- **Language**: TypeScript (`tsconfig.base.json`: strict, `exactOptionalPropertyTypes`, `noImplicitOverride`, `erasableSyntaxOnly`, `isolatedModules`), compiled twice from the same sources
- **Testing**: Node.js test runner (`node:test`) through `tsx`, coverage with c8
- **Lint/format**: ESLint with typescript-eslint (`eslint.config.js`, flat config) + Prettier; `npm run lint` runs the type-check first, then ESLint. `src/` is also linted with the type-aware rules (floating and misused promises, unnecessary type assertions, deprecated APIs); a promise that is deliberately left unawaited is marked with `void`. The rule set is the shared one (`../nodemailer/eslint.config.js` is the canonical form); repo-specific overrides go in the "Repo-specific" block near the end, each with a one-line reason (`no-await-in-loop` is off there because commands on one connection are awaited in sequence on purpose)
- **Key dependencies**: `@zone-eu/mailsplit`, `libmime`, `libqp`, `libbase64`, `iconv-lite`, `encoding-japanese`, `pino`, `socks`

## Engine target and module format

- `engines.node = ">=20.0.0"`. TypeScript `target: ES2022` with `lib: ES2023`. `@types/node` is pinned to the 20.x line (see `.ncurc.cjs`) so the compiler rejects APIs that do not exist on Node 20.
- Source uses ES module syntax and is compiled twice from the same files: `tsconfig.esm.json` (`module: nodenext`) into `dist/esm/` and `tsconfig.cjs.json` (`module: commonjs`) into `dist/cjs/`. Because every file must compile both ways, code under `src/` must not use `import.meta`, `require`, `module`, `exports`, `__dirname`, `__filename`, top-level `await`, or JSON imports.
- `erasableSyntaxOnly` is on: no enums, no namespaces with runtime code, no parameter properties, no decorators. Use `as const` objects instead of enums.
- `exactOptionalPropertyTypes` is on. Every optional property of a public interface is declared with an explicit `| undefined` (`readOnly?: boolean | undefined`), so a consumer compiling with that flag can still pass a value that may be undefined. `test/package/types-consumer-test.ts` checks this against the built declarations.
- `ImapFlow` extends the plain `EventEmitter`, not `EventEmitter<ImapFlowEvents>`, so the declarations do not depend on the generic EventEmitter that only newer `@types/node` releases have. The typed events come from the `ImapFlow` interface merged with the class in `src/imap-flow.ts`, one overload generic over `ImapFlowEvents` per emitter method plus the string catch-all of the base class; a new event only needs an entry in `ImapFlowEvents`. `test/package/types-consumer-test.ts` type-checks a consumer against `types-node-legacy`, an alias of the oldest `@types/node` of the supported Node line that `.ncurc.cjs` keeps out of `npm run update`.
- Relative imports always carry the `.js` extension and point at a file (`'../tools.js'`), never at a directory.
- Node builtins are imported with the `node:` prefix. Use a default import (`import net from 'node:net'`) when the whole module is used, so tests can still stub methods on it with `t.mock.method()`; use named imports otherwise. Do not use `import * as` for builtins.
- Tests are ES modules too (`.ts`, run through `tsx`). They may use `import.meta.url`.

## Export shapes

- Modules that used to be `module.exports = fn` (every `src/commands/*.ts` command, `src/handler/imap-parser.ts`, `src/handler/imap-compiler.ts`, `src/handler/imap-formal-syntax.ts`, `src/imap-commands.ts`, `src/logger.ts`) have exactly one runtime export, `export default`. The build rewrites their CommonJS output so `require()` returns the value itself (a non-enumerable `.default` alias is kept for transpiled default imports). Such modules must not gain other runtime exports; type exports are fine. Helpers that commands share (`copyuid-parser.ts`, `status-fields.ts`, `esearch-parser.ts`, `subscription.ts`) live in their own named-export modules, and a command file stays in place as a thin default export even when its body moves there, because `imapflow/lib/commands/<name>` deep imports resolve to it.
- Everything else uses named exports only. `src/imap-flow.ts` is the one mixed module (named exports plus a default export object) and is listed in `MIXED_EXPORT_MODULES` in `scripts/build.js`.
- The declarations are generated with `stripInternal`. Every member of `ImapFlow` and every helper type in `src/imap-flow.ts` that is not part of the public API (the documented methods and properties, the connection facts such as `state`, `namespace`, `greeting` or `tls`, and the types the public signatures use) carries `@internal` in its JSDoc, so it exists at runtime but is absent from the shipped `.d.ts`. A new internal member needs the tag, a new public one needs a doc comment without it. `test/package/types-consumer-test.ts` checks that a consumer cannot reach the internals.
- `package.json` `exports` maps `.` to both builds and `./lib/*` to the matching file under `dist/`, so a `require('imapflow/lib/tools')` style deep import keeps resolving.

## Testing

- Tests live in `test/` and are named `*-test.ts`; `npm test` runs every such file except `test/integration/**` (needs Docker, `npm run test:rev2` and `npm run test:james`), `test/cloudflare/**` (needs workerd, `npm run test:workers`), `test/celld/**` (needs Docker, `npm run test:celld`) and `test/browser/**` (needs Chrome, `npm run test:browser`).
- `npm test` builds first (`pretest`), because `test/package/` loads the built `dist/` output through the `exports` map the way an installed copy is loaded. Keep the suite green and lint-clean before committing.
- Tests use `describe`/`it` from `node:test` and `assert` from `node:assert/strict`. A test that completes inside a callback takes the `done` parameter (`it('...', (t, done) => { ... })`); an async test returns a promise. Module methods are stubbed with `t.mock.method()` on the imported module object, never by replacing the module.
- The suite runs serially (`--test-concurrency=1`): several suites swap `globalThis.setTimeout` through `test/fixtures/fake-timers.ts`.
- The `test` scripts pass `--test-force-exit`, so a test that leaves a socket or a server open still finishes with its result instead of hanging the run until the CI job timeout. Where cleanup is the point of a test, assert it explicitly (`test/timer-policy-test.ts`, `test/memory-leak-test.ts`), the flag does not report leaked handles.
- New tests go in `test/` as `*-test.ts`. The parser, command compiler, and search compiler are the most security-sensitive areas - add hostile/malformed-input cases there.
- Seeded fuzzing: `test/parser-fuzz-test.ts` generates server responses together with the structure the parser must produce (`test/fixtures/imap-fuzz.ts`) and checks the parse result against it, chunk-split invariance of the stream framing, compile-then-parse round trips, that corrupted input fails only with coded errors (never a TypeError or RangeError), and that no compiled command value can break out of its command. `test/client-fuzz-test.ts` plays generated and corrupted responses at a real client and checks that every pending command settles and nothing escapes as an unhandled rejection. `FUZZ_SEED` and `FUZZ_ITERATIONS` control a run; a failure message names its seed and case, reproduce with `FUZZ_SEED=<seed> FUZZ_ITERATIONS=<n>` (and `FUZZ_CASE=<n>` with a debug logger for the client suite). Raise `FUZZ_ITERATIONS` for a soak run after touching `src/handler/`.
- Heap budgets: `test/heap-budget-test.ts` runs a session against the CommonJS build in a child process capped with `--max-old-space-size`, so a response that costs many times its own size while it is parsed aborts the child instead of passing unnoticed (the byte limits bound what a server sends, not what the client makes of it). A change to how a large response is parsed or accumulated (SEARCH, ESEARCH, FETCH, LIST) gets a scenario there, with the cap at about twice what the scenario needs. Skipped on Bun.
- Server quirks are pinned as transcripts in `test/fixtures/transcripts.ts` (format in `test/fixtures/transcript-server.ts`: `S:` lines are sent, `C:` lines are the commands the client must send) and replayed against a real client by `test/transcript-replay-test.ts`. A new server quirk gets a transcript there. Captured real sessions that can not be committed are checked locally with `IMAPFLOW_TRANSCRIPT_DIR=/path/to/dir npm test` (every server line of each `*.txt` transcript must parse).
- `test/fixtures/scripted-server.ts` is the shared scriptable mock server for end-to-end client tests (defaults for a full session, `handlers` override single commands).
- `npm run test:mutation` (`scripts/mutation-test.js`) applies one-operator mutants to the parser, stream, compiler and search compiler in private copies of the repository and lists the mutants no test catches. Not part of CI; run it after larger changes to those files and either add a test for a surviving mutant or confirm it is equivalent. `--file <path>` limits it to one file, `--survivors <json>` re-runs the survivors of an earlier run.
- `test/imapkit/` runs real sessions against [ImapKit](https://github.com/postalsys/imapkit) (devDependency `imapkit`), a strict in-memory IMAP server started in-process, one per test, through `startImapKit()` in `test/fixtures/imapkit.ts`. Use it for what the Docker servers can not set up: any capability set (fallback paths), OAuth and LOGINDISABLED logins, Gmail X-GM-EXT-1, quota and append limits, several sessions on one mailbox, preset mailbox state. ImapKit answers RFC violations with BAD and the fixture fails a test on any BAD, so the suite also checks the syntax the client sends. Faults (canned or dropped responses, output cut short, split or delayed, unsolicited responses, dropped connections) are ImapKit script rules (`script` server option or `kit.script.add()`), see `test/imapkit/faults-test.ts`. Changes made on the server outside any session (flags, expunges, new messages, a new UIDVALIDITY, injected output, disconnects) go through the control API (`kit.control`, `test/imapkit/server-changes-test.ts`), and `kit.serverEvent()` waits for a server event such as the session entering IDLE. Known real server bugs run as ImapKit quirk presets with several seeds (`test/imapkit/quirks-test.ts`: Apache James, Yahoo, Microsoft 365 throttling), so they are covered in every run without the Docker suites. `kit.control.getMessage()` checks what the client stored, byte for byte. A server-side bug found there is filed on postalsys/imapkit (or postalsys/imap-handler for the parser) and the test is skipped with a link to the issue. When a test would need a workaround because ImapKit lacks a capability, the capability is requested on postalsys/imapkit instead.
- `npm run test:rev2` starts a Dovecot 2.4 container (real IMAP4rev2 server) and runs `test/integration/rev2-live-test.ts` against it - use it to verify rev2-facing changes end to end, mocks alone are not enough.
- `npm run test:james` starts Apache James (`apache/james:memory-*`, the base of hosted services such as Twake Mail) and runs `test/integration/james-live-test.ts` against it, with a fresh user per test created through the WebAdmin API. James deviates from Dovecot in ways mocks do not show (it drops the second section asked for one MIME part in a FETCH, advertises QRESYNC without CONDSTORE), so changes to fetch, download, search, flags or sync get a run here too. A newly found James quirk gets a live test there and a transcript in `test/fixtures/transcripts.ts`.

## Other runtimes

- **Bun**: `npm run test:bun` runs the whole suite (package tests included) with `bun test`, which understands the `node:test` imports and runs every file in one process. CI runs it on the latest Bun release; older Bun versions are not a target. `test/fixtures/fake-timers.ts` gives its fake handles `refresh()` and `hasRef()` because Bun's sockets keep their inactivity timer through the global `setTimeout`. A test that spawns a child runtime must skip the tsx loader when `process.versions.bun` is set.
- **Cloudflare Workers**: `npm run test:workers` builds `dist/`, then `test/cloudflare/cloudflare-test.ts` starts `wrangler dev` (a local workerd with `nodejs_compat`) on `test/cloudflare/worker.ts`, which imports the ES module build and runs a session against the scenario it is posted. Cases cover cleartext, COMPRESS=DEFLATE (`node:zlib`), the default pino logger, and implicit TLS against a throwaway Ethereal account (skipped when the account API is unreachable). The API tour (`runTour()` in `test/fixtures/api-tour.ts`, checked by `test/fixtures/api-tour-server.ts`) drives most of the public API (mailbox management, STATUS, FETCH of structure and parts, `download()` and `downloadMany()`, flags, SEARCH, COPY, MOVE, EXPUNGE, QUOTA) against an ImapKit server with every plugin, started in the test process; it runs over `node:net` and over `createSocketsTransport()`, and a public API change that matters on these runtimes gets a step there. `worker.ts` is excluded from the type-check because it imports the build output. Wrangler keeps its state in `.wrangler/` (gitignored).
- Workers limitations, documented in the README and pinned by the harness: workerd refuses `tls.rejectUnauthorized: false` (`ERR_OPTION_NOT_IMPLEMENTED`), returns `null` from `getCipher()` (normalized to `false` in `client.tls`), and can only upgrade a socket to TLS when no read is pending on it, which an asynchronous STARTTLS exchange can not guarantee, so a STARTTLS upgrade over `node:net` fails there with `tlsFailed` set. Through `createSocketsTransport()` it works: the transport stops reading once the STARTTLS OK arrived and releases the stream locks before `startTls()`. Its `process.nextTick` is a microtask, so a `'readable'` event can fire while the reader loop is still winding down; the loop re-checks the parser buffer after it ends (`test/runtime-compat-test.ts`).
- **celld** (<https://celld.dev/>): `npm run test:celld` builds `dist/`, then `test/celld/celld-test.ts` runs `celld dev` in Docker (`ghcr.io/denoland/celld`, host networking, with a linux esbuild fetched into `.celld/`) on `test/celld/worker.ts`, which reuses the scenarios of the Workers harness, the API tour included. CI runs it in the `test-celld` job. celld has no `node:net`, `node:tls` or `node:dns` (they throw "not implemented in celld"), so sessions use the `transport` option with `createSocketsTransport(connect)`. Pinned there: certificates are always verified (TLS options that would change that are refused with `UnsupportedTransportOption`), no streaming zlib (COMPRESS is skipped), `startTls()` with a read in flight never completes, and a socket is closed when the request that opened it ends (`ctx.waitUntil()` keeps it alive).
- **Browser**: `npm run test:browser` builds `dist/`, then `test/browser/browser-test.ts` bundles `test/browser/page.ts` with esbuild the way an application would (`node:stream` from readable-stream, `node:events` from events, `Buffer` from buffer, `node:crypto`, `node:zlib`, `node:net`, `node:tls`, `node:dns` and `path` from the shims in `test/browser/shims/`, and the `Buffer`, `process`, `setImmediate` and `clearImmediate` globals injected from `shims/globals.js`) and runs it in headless Chrome through playwright-core (the installed Chrome, or `CHROME_PATH`; skipped without one). Sessions run over in-memory connections to the browser build of ImapKit (`imapkit/browser`) in the same page: the API tour through `createStreamsTransport()` with a STARTTLS upgrade (ImapKit's `startTls()` without TLS), and through a hand-written Duplex transport without OBJECTID, so message ids go through the MD5 shim. CI runs it in the `test-browser` job. A new Node.js builtin or a new use of one in `src/` (or in a dependency) needs a shim there.
- The API tour (`test/fixtures/api-tour.ts`) is runtime neutral: it only gets a client, so each harness passes one of the build it loads.
- Keep `src/` free of runtime detection. Portability is achieved by not relying on Node-only ordering or on socket features that other runtimes stub (`setKeepAlive` is a no-op on workerd), and every such spot gets a test in `test/runtime-compat-test.ts`.

## Platform constraints (IMPORTANT)

EmailEngine (see "Relationship to EmailEngine" below) bundles ImapFlow and all
of its transitive dependencies into a single self-contained executable using
[`@yao-pkg/pkg`](https://github.com/yao-pkg/pkg). `pkg` works by snapshotting a
CommonJS `require()` graph, so it **cannot load ES modules**. Two rules follow:

- **Node.js 20 is the minimum supported version.** Runtime code, tests and tooling must work on Node 20, 22 and 24 (see "Engine target and module format" above).
- **The CommonJS build in `dist/cjs/` and every runtime dependency it pulls in must be genuinely CommonJS-loadable**, with `require(esm)` switched off. Node 22+ (and 20.19) load ES modules through `require()` by default, which hides an ESM-only dependency until the pkg binary fails on it. A CommonJS entry that only wraps a dynamic `import()` of ESM code does not count.

What that means in practice:

- Keep the dual build. Never drop the CommonJS output or make the CommonJS entry depend on ESM-only syntax.
- Do not add a dependency that is pure ESM (`"type": "module"` with only an `import`/ESM entry and no CommonJS export). A `"type": "module"` package with a `require` condition in its `exports` (libmime, libqp, libbase64) is a dual package and is fine.
- Never upgrade to an ESM-only major. When `npm run update` or a new dependency would pull one in, pin the last CommonJS major in `.ncurc.cjs` (`reject`, or a `target` of `minor`/`patch`) with a comment giving the reason, or find a CommonJS alternative.
- **Check with `npm run test:cjs`** after every dependency change. It builds `dist/`, then `test/package/cjs-smoke.cjs` requires the entry `exports.require` points to (and a few deep imports) under `NODE_OPTIONS=--no-experimental-require-module` and runs a short session against an in-process server. It is plain JavaScript on purpose: tsx's loader would transpile an ES module dependency and mask the failure. CI runs it on Node 22.x and 24.x (Node 20 has no such flag). To list pure-ESM production dependencies directly:

    ```
    node -e "const fs=require('fs');const bad=Object.keys(require('./package.json').dependencies).filter(d=>{const j=JSON.parse(fs.readFileSync(require.resolve(d+'/package.json'),'utf8'));return j.type==='module'&&!JSON.stringify(j.exports||{}).includes('\"require\"')});console.log(bad.length?'PURE-ESM DEPS FOUND: '+bad.join(', '):'No pure-ESM production dependencies')"
    ```

- pino reaches `real-require`, which does a dynamic `import()`, but only to load pino transports (worker-thread targets set through `transport` or `pino.transport()`). ImapFlow never uses them: the only pino call is `pino({ level: 'info' })` in `src/logger.ts`. Keep it that way, a transport would put an ES module load inside the pkg binary.
- Keep `require()`/`import` paths static so `pkg` can trace the graph; avoid building module paths at runtime.
- Dev tooling has its own constraints: typescript-eslint's peer range excludes TypeScript 7, so `typescript` stays on the 6.x line (`.ncurc.cjs` pins it to minor updates).

## Code Style Rules

- Never use emojis in code or documentation, only printable ASCII characters.
- Use a single hyphen-minus (`-`) as a dash in user-facing strings and docs. Never use double hyphens (`--`), em dashes, or en dashes.
- Every options object a method reads has an exported interface in `src/types.ts` (or next to the code that reads it, for internal ones), and every optional property carries `| undefined`.
- Coded errors are built with `createImapError(message, code, props?)` from `src/errors.ts`, which returns an `ImapFlowError` and type-checks `code` against `ImapFlowErrorCode` (or a numbered `ParserErrorN`). A new code gets an entry in `ImapFlowErrorCode`. Do not invent new ad-hoc error properties without adding them to `ImapFlowError`.
- Prefer small, surgical diffs. The codebase is mature and load-bearing - avoid drive-by refactors or comment churn outside the scope of the change.
- When composing git commit messages, do not include Claude or any AI assistant as a co-contributor (no `Co-Authored-By` trailer).
- Use Conventional Commit prefixes (`feat:`, `fix:`, `chore:`, `docs:`, `test:`, `ci:`, ...). Versioning and the changelog are driven by these prefixes via release-please.
- For commits that do not change published runtime behavior (docs, comments, CI/workflow tweaks, formatting), append `[skip ci]` to the commit message to avoid triggering the GitHub Actions workflows. Exception: do not add `[skip ci]` to commits using a `fix:` or `feat:` prefix - those must run so the release action is triggered.
- After making code changes:
    1. Run `npm run format` and `npm run lint`
    2. Run `npm test` and keep it green
    3. For non-trivial changes, run `/simplify` to review changed code and `/security-review` to check for security issues before committing
- After pushing, check the GitHub Actions runs for the push (e.g. `gh run list --branch master`) and report their status. If a run fails for a strange or unrelated reason (for example a checkout step reporting "account suspended", HTTP 403, or other auth/infrastructure errors that have nothing to do with the change), check <https://www.githubstatus.com/> for an active GitHub incident before assuming the failure is caused by the change.

## Relationship to EmailEngine

ImapFlow is developed and maintained primarily as the IMAP client used by
[EmailEngine](https://github.com/postalsys/emailengine). The local development
copy of EmailEngine lives at `../emailengine` relative to this project root. When
EmailEngine hits a bug or unhandled promise rejection that originates in
ImapFlow, the fix belongs here in the ImapFlow source rather than as a
workaround in EmailEngine. Because EmailEngine packages this library with
`@yao-pkg/pkg`, never make a change here that breaks CommonJS packaging (see
Platform constraints).

## Release Process

Changelog and version numbers are managed automatically by the release-please GitHub Action. Do not check for or suggest CHANGELOG entries or version bumps during code reviews. The `prepare` script builds `dist/` on install and before publish, so build output is never committed.
